# C · MemOS 架构调研与可借鉴点

> 2026-10-17 读 MemTensor/MemOS 的 `apps/memos-local-plugin`（Reflect2Evolve）。
> 目的：为 B 线（提取重做）找参照，判断哪些设计值得抄。

## 一、它的四层记忆

| 层 | 是什么 | 回答的问题 |
| --- | --- | --- |
| **L1 trace** | 一次 `(think + 动作 + 观测)` 的落地记录，带反思与价值分 | 这一步做了什么、发生了什么 |
| **L2 policy** | 跨任务归纳出的子任务策略（trigger / procedure / verification / boundary） | 在这种条件下该怎么做 |
| **L3 world model** | 多条同领域策略背后抽象的环境认知（空间结构 / 行为规律 / 约束禁忌） | 这个环境长什么样、什么不能做 |
| **Skill** | L2 + L3 打包成可调用对象 + 持续修订的可靠性 | 当前 query 该不该调这条策略 |

## 二、最关键的一个设计：粒度锁死

它把三个粒度分得很清楚，而且**算法只用两个**：

| 粒度 | 内容 | 算法可见性 |
| --- | --- | --- |
| **小步 step** | 一次 (think + 动作 + 观测) | ✅ 有分（α 反思权重 + V 步价值） |
| **任务 task / episode** | 同一 topic 的多个轮 | ✅ 有分（R_human 终局奖励） |
| **轮 turn** | 用户感知的一次问答 | ❌ **算法完全不看**，只在前端展示层聚合 |

**为什么这点重要**：我们现在的记忆就是按「轮」切的——每轮结束提取一次，所以天然产生碎片。
MemOS 的答案是把「轮」从算法里彻底剔除：检索按小步（精准）或按子任务（上下文完整），从不按轮。

## 三、打分机制：反思加权回溯

```
任务结束 (episode.finalized)
   ↓ 一次 LLM 批量调用
   ├─ 算 R_human（任务级，1 个标量，三轴 rubric：目标/过程/满意度）
   └─ 给任务内每个小步打 α_t（反思权重，N 个）
   ↓ 回溯
   V_T = R_human
   V_t = α_t · R_human + (1-α_t) · γ · V_{t+1}
   ↓
写回每条 trace 的 reflection / alpha / value
```

**要点**：
- 不是每个小步发生时都跑 LLM 打分，而是**任务结束时一次性批量打**
- R_human 是任务级唯一信号，回溯到每个小步——不问用户「这一步好不好」
- α 由反思识别「关键发现」的高低决定（关键步 α 高、闲聊步 α 低）

## 四、它的写入时机（与主人要的设计吻合）

MemOS 的 capture 管线是：**任务结束（episode.finalized）→ 才捕获成 L1 trace**，不是每轮结束。
这和主人说的「会话静置 12 小时后才提取」是同一个思路——只是它用「任务边界」判定，主人用「时间静置」判定。

## 五、三层检索（按需，不按轮）

| 层 | 触发时机 | 召回粒度 |
| --- | --- | --- |
| Tier-1 技能 | 新任务到来 | 一个完整技能对象 |
| Tier-2a 单步 | 当前小步执行失败 | 1 条小步（精准对症） |
| Tier-2b 子任务序列 | 当前子任务目标与历史相似 | N 条连续小步 |
| Tier-3 环境认知 | 反思出现**结构性不确定** | 一个环境认知对象 |

「结构性不确定」的判别（值得抄）：反思里出现 *不确定 / 哪一层 / 是不是因为 / 副作用 / 影响范围* 等结构性词汇，
或遇到 embedding 在历史里都找不到相似的全新状态。操作性问题（如「换个命令试试」）不触发第三层。

## 六、可借鉴到 dsh-memory 的部分（按价值排序）

### 高价值：可以直接抄

1. **粒度分离**：把「轮」从提取与检索的算法里剔除。提取按「会话段/任务」，检索按「条目」或「条目序列」。
   我们现在的碎片问题，根子就在「每轮一提」。
2. **候选池 + 归纳门槛**：MemOS 的 L2 有个 `candidate_pool`，键是 `signature = primaryTag|secondaryTag|tool|errCode`，
   **同一个桶攒够 N 个不同 episode 才归纳成一条策略**。这正好解决「碎片直接入库」——碎片先进候选池，攒够了才合并成条目。
3. **任务结束才批量打分/提炼**：一次 LLM 调用处理整段，而不是每轮一次。省成本，且能看到全局。
4. **派生字段回写判空**（我们已踩过）：MemOS 的 merge 有 cosine 阈值与冷却，我们这边是 theme 被空值覆盖。

### 中价值：思路可借，实现要改

5. **反思权重 α**：给每条记忆算一个「这条有多关键」的权重，而不是只靠 strength 衰减。
   我们可以用「提取时模型自评」替代它的 rubric 打分。
6. **三层检索**：技能 → 条目 → 世界模型。我们目前只有「条目」一层。
   可以先加「条目序列」（同一会话/同一任务的连续条目），技能层留到以后。
7. **结构性不确定才深挖**：检索时判断「这个问题是不是需要环境级认知」，避免每次都全量检索。

### 低价值 / 不适合

8. **团队共享 hub**：我们单人使用，不需要。
9. **多适配器（OpenClaw / Hermes / DSH）**：我们只服务 DSH。
10. **viewer 十视图**：我们已有记忆图谱与日志面板，不必重做。
11. **YAML 单一配置 + 独立 runtime home**：我们有 DSH 的 settings 体系，不必另起。

## 七、对 B 线（提取重做）的直接结论

主人要的设计与 MemOS 高度一致，差异只在**触发判据**：

| 维度 | 主人要的 | MemOS 做的 | 建议 |
| --- | --- | --- | --- |
| 触发 | 会话静置 12 小时 | 任务结束（episode.finalized） | **两者结合**：任务结束 或 静置 12 小时，先到先触发 |
| 读取 | 分批读整段会话 | 按 episode 读 | 一致 |
| 提取 | 分批提取 | 一次批量（任务结束统一打） | **分批**，但每批是「一个 episode」 |
| 整合 | 全部提完再整合分类 | L2 候选池攒够 N 个才归纳 | **抄候选池**：碎片先进池，攒够门槛才合并入库 |
| 入库 | 整合后才入库 | L1 立即入库、L2 才归纳 | 我们应改为**入库前整合**（主人明确要求） |

**一句话结论**：主人要的方案比 MemOS 更严格（入库前整合 vs 入库后归纳），
MemOS 的**候选池 + 门槛**机制是把这个严格方案落地的最合适工具。
