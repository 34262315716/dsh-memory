# B · 提取机制重做

> 主人 2026-10-17 提出的方案。当前状态：**仅记录，未开工**。

## 一、现状的问题

现在的提取是**每轮对话结束就触发一次**（`turn/end` → 价值门 → 决策门 → LLM 提取）。后果：

- 一次会话里同一件事被反复提取，产生大量碎片
- 每轮只看到「这一轮」，看不到「整段会话落在哪里」
- 提取完直接入库，**没有全局整合环节**，所以碎片直接进库

## 二、主人要的设计

### 触发时机

**会话超过 12 小时不动之后**才启动提取，而不是每轮结束就提。

含义：一次会话（可能跨很多轮）整体静置 12 小时，视为「这段工作告一段落」，才开始整理。

### 提取方式

1. AI **看一遍整段会话的过程**（不是只看最后几轮）
2. **分批次读**，不是一次性全部注入——避免上下文爆掉
3. **分批次提取**，边读边提
4. 全部提完后，**对提取出来的记忆做一次完全的整合分类**
5. 整合完才**进入记忆数据库**

### 这样能解决什么

- 杜绝「太散」：整段会话只提一次，同一件事不会被反复提取成碎片
- 杜绝「无效」：有整合分类环节，碎片在入库前就被合并
- 降低成本：不需要每轮都跑一次 LLM

## 四、与 A 线的关系

A 线是**存量清理**（把已经散掉的合回来），B 线是**增量治理**（让以后不再散）。
B 线做完，A 线的问题不会再生；但 A 线的存量还得清。

## 六、读 MemOS 后的结论（2026-10-17）

详见 [C-MemOS架构调研.md](C-MemOS架构调研.md)。要点：

1. **主人要的方案与 MemOS 高度一致**，差异只在触发判据：MemOS 用「任务结束」，主人用「静置 12 小时」。
   建议两者结合——**任务结束 或 静置 12 小时，先到先触发**。
2. **MemOS 的「候选池 + 门槛」机制正是落地工具**：
   - 碎片先进候选池，不直接入库
   - 候选池按 signature（主题|工具|错误码）分桶
   - **同一个桶攒够 N 个不同 episode 才归纳成一条条目**
   这正好解决「碎片直接入库」的问题，且比单纯的「合并」更有依据。
3. **粒度分离**：「轮」从算法里彻底剔除。提取按会话段/episode，检索按条目或条目序列。
   我们现在的碎片问题，根子就在「每轮一提」。
4. **任务结束才批量打分**：一次 LLM 调用处理整段，省成本且能看到全局，而不是每轮一次。

### 修正后的 B 线设计草案

```
会话静置 12h 或 任务结束
   ↓
① 分段读取整段会话（按 episode 边界或 token 预算切）
   ↓
② 每段提取候选（不进库，进候选池）
   ↓
③ 候选池按 signature 分桶，攒够 N 个才归纳
   ↓
④ 对归纳结果做一次全局整合分类（去重、合并、定 scope）
   ↓
⑤ 整合完才写入记忆库
```

对比现在的流程：

```
每轮 turn/end
   ↓
价值门 → 提取 → 直接入库（没有候选池，没有整合）
```
## 七、落地状态（2026-10-17）

**已实现并开启。** 触发条件按主人最终决定改为：**会话 2 小时无新消息即开始提取整合**（原定 12 小时）。

### 配置项（`lib/config.js` → `batchExtract`）

| 项 | 默认值 | 含义 |
| --- | --- | --- |
| `enabled` | **true** | 开启后 turn/end 只累积轮次，不再逐轮提取入库 |
| `idleHours` | **2** | 静置多少小时无新消息后触发 |
| `segmentTurns` | 12 | 单段最多几轮（控制单次 LLM 输入） |
| `minSessions` | 2 | 归纳门槛：同桶至少来自几个不同会话 |
| `maxBucketsPerRun` | 8 | 每轮最多归纳几个桶 |
| `scanIntervalMin` | 10 | 后台扫描间隔（分钟） |

### 实现文件

| 文件 | 职责 |
| --- | --- |
| `lib/session-batch.js` | 分段、签名、静置判定、归纳、整合 |
| `lib/session-persist.js` | 累积轮次落盘（meta 表），跨重启不丢 |
| `lib/pipelines/write.js` | turn/end 累积分叉、后台扫描定时器、会话销毁处理 |
| `lib/store.js` | `memory_candidates` 表 + 6 个候选池方法 |

### 两个必须记住的实现细节

1. **累积必须落盘**：静置计时器活在内存里，进程重启就没了。不落盘的话，只要 2 小时内重启过一次，那段会话永远等不到提取。现在存在 meta 表的 `batch:turns:<sid>` 键下，启动时读回。
2. **会话销毁时不能清累积**：`agent/disposed` 原来会 `sessionTurns.delete(sid)`，那会把还没静置够的轮次直接扔掉。现在批量模式下保留，并立刻检查一次是否已够久。
